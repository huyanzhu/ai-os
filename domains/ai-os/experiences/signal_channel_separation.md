# Knowledge: 单文件双通道会 mtime 回环——信号通道必须按方向分离

**来源**: done.signal v2 真实瑕疵（2026-08-05，用户发现）
**日期**: 2026-08-05
**类型**: 系统观察 / 设计教训

---

## 内容

完成信号机制（done.signal）v2 版把"完成通知"和"回复占位"放在**同一个文件**：Agent 写完成信号（mtime 变）→ 助理 bot watcher 触发通知用户 → 用户/助理在 reply 占位写回复 → Agent 轮询读到后**清空 reply 占位**（覆盖写同一文件，mtime 又变）→ 助理 bot watcher **再次触发** → 用户收到第二条"完成"假通知，或把清空动作误认为新完成信号。

**根因**：一个文件同时承载两个方向的信号（Agent→用户 的完成通知、用户→Agent 的回复），写者不同、读者不同、监听者却只能靠 mtime 区分——Agent 自己的清空动作与"新完成信号"在 mtime 上不可区分，形成反馈回环。

**解法 = 双通道分离**：
- `done.signal`：完成通知（Agent→用户），唯一写者=Agent，唯一监听者=助理 bot
- `reply.signal`：回复（用户→Agent），唯一写者=助理/用户，唯一读者=Agent（读后清空，不影响 done.signal 的 mtime）

**普适判据**：一个文件若被多个方向写入/读取，且有人依赖 mtime/内容变化作为"发生了新事件"的判据——**一条通道一个文件，一个方向一个写者**；清空/确认动作必须发生在不承载"事件语义"的文件上。

**方向**：单文件承载多方向信号 = 信号语义污染；任何"完成/确认/ack"类机制都按此设计。AI-OS 造前遍历时如遇"一个文件两个方向"的设计，直接按此判据拆。

**2026-08-06 注记**：done.signal 协议已由用户裁定**简化回单向**（只需"做完→写→助理监听→通知"，reply 通道与轮询窗口全部移除）——当前机制不再涉及双通道，本教训不再约束现行协议；但仍作为**普适设计判据**保留：未来任何机制若出现"一个文件两个方向 + 依赖 mtime 判事件"，直接套用此判据（一条通道一个文件，一个方向一个写者）。
